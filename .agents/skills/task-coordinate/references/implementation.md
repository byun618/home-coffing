# 구현 워커 실행 절차

task-coordinate §4에서 기동 전에 읽는다. **이 문서에는 도구 명령이 없다** — 능력 이름은 겹낫표로 감싸 적고,
명령·플래그·거절 코드·수치 상한은 선택한 하네스 매핑(`.agents/harness/<도구>.md`)에서 읽는다.
능력 이름과 보장 어휘의 정본은 `.agents/harness/capabilities.md` 다.
매핑에 없는 것을 짐작해서 치지 않는다.

## 1. 준비와 산출물 소유권

- 작업의 모든 역할 모델/effort는 00-start의 기록을 따른다(기본값은 `.agents/defaults.md`).
  명시 변경이 있으면 해당 CLI가 실제 지원하는 옵션으로 반영한다.
  **실제 해소 모델·advisor 활성화는 『세션 기동』의 관측(프로세스·argv, 배너)으로 기록한다** —
  기동 시점 스냅샷은 갱신되지 않는다. 별칭은 버전 고정이 아니니 요청값과 관측값을 구분한다.
  필요하면 advisor picker를 **조회 후 취소**한다 — 전역 설정을 저장하지 않는다.
- 제품은 워커가 구현 브랜치에 커밋하고, 구현 raw 는 작업 폴더 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/raw/<도구>/` 에 절대경로로 직접 쓴다
  (커밋하지 않는다). 분석·기준·킥오프·리뷰 기록·최종 verdict 와 raw 커밋은 코디네이터가 작업 폴더에 한다
  (AGENTS.md 「산출물 규칙」). **별도 설계 문서는 만들지 않는다.**
- 리뷰어는 고정 commit의 코드와 작업 폴더의 원자료를 읽고 결과를 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/raw/review/<도구>-rN.md` 에 직접 쓴다.
  리뷰어는 git commit/add도, 구현자 파일 수정도 안 한다.
- 워커에게 기준·판정 문서는 작업 폴더 절대경로와 그 시점 산출물 커밋 해시로 알려 준다 — 해시는 「무엇을 기준으로
  받았나」의 기록이고, 읽기는 경로로 한다. 리뷰를 위해 제품을 먼저 머지하지 않는다.
- **일감 전용 관문 스크립트는 작업 폴더 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/scripts/` 에 둔다.**
  코드 레포에는 커밋하지 않는다.
  worktree 경로는 절대경로 인자·환경변수로 받고 앱 소스·의존성은 그 경로 기준으로 읽는다 — 스크립트가 worktree 밖에 있으므로
  소스를 상대 import 로 읽지 않는다.
  <!-- paddock:design D9 -->
  node 스크립트(`.mjs`, Node 20). 첫 인자 = worktree 절대경로. 실행: `node <작업 폴더>/scripts/<이름>.mjs <worktree>`.
  의존성은 worktree 루트 `node_modules`(pnpm `nodeLinker: hoisted`)에서 `createRequire(path.join(wt, 'package.json'))` 로 읽고, 빌드 산출물은
  `<wt>/apps/api/dist` 기준으로 동적 `import()` 한다. 테스트 러너는 없다. DB 에 쓰는 관문은 만들지 않는다(validation.md D6).
  <!-- /paddock:design -->
  작업 폴더 `scripts/` 는 다른 원자료와 같이 코디가 게이트 시점에 자기 폴더로 커밋한다(워커·리뷰어는 커밋하지 않는다). 코드 레포에는
  되풀이해 쓰는 시험·도구만 하는 일 이름으로 둔다 — 시험은 검사 대상 옆, 도구는 레포의 스크립트 폴더에 `<하는 일>/` 로, 경로에 일감 번호 없이.
- native advisor는 서버에서 워커의 대화를 받아 상담한다. 별도 구현자·독립 리뷰어로 세지 않고, 호출 시점·
  횟수는 모델이 정한다. 어려운 판단에서 상담하도록 지시하되 "1회 상한"이나 별도 advisor effort를 지원한다고
  쓰지 않는다. 실제 상담 여부·실패/미사용은 워커 보고와 transcript로 확인한다.
  **advisor 조언 자체는 리뷰 지적이 아니다.**

## 2. 구현 워커 기동 준비

1. 킥오프 승인 후 작업 브랜치 HEAD에서 구현 브랜치와 형제 worktree를 만든다. 기존 것이면 재사용 여부부터 확인한다.
   제어 도구에 repo setup/archive hook이 없는 환경이면 기다릴 setup 단계도 없다 — 준비 확인은 worktree
   생성 결과로 한다.

```bash
# 본체 절대경로를 REPO_ROOT에, 현재 작업 브랜치를 TASK_BRANCH에, 구현 도구 접미사를 IMPL(예: -claude)에 지정한 뒤 실행
git -C "$REPO_ROOT" worktree add "$REPO_ROOT/.claude/worktrees/${TASK_BRANCH}${IMPL}" \
  -b "${TASK_BRANCH}${IMPL}" "$TASK_BRANCH"
```

   접미사는 `.paddock/config.sh` 의 `VARIANT_SUFFIXES` 중 하나여야 한다 — `task-finish.sh` 가 그 이름만 버려도 되는 변형으로 보고 정리한다.

2. 『제어 문맥 격리』를 먼저 정한다 — **내 작업의 기존 Run**(내가·내 세션이 이 일감으로 만든 것)을 우선 쓰고,
   없거나 **누구 것인지 모르면 새로 만들고 끝나면 복원한다.** **어느 명령에 Run을
   명시하는지는 매핑의 Run 명시 규칙을 따른다** — 받지 않는 명령에 붙이면 거절되는 도구가 있다.
   바인딩을 바꿨다면 바꾼 쪽이 복원하고 복원을 확인한 기록을 남긴다. 남의 Run·pane을 밟지 않는다.

**소유권**: 내가 띄운 pane은 그 시도가 **소유**하고, 사람이 만들어 준 pane은 처음부터 **빌린 것**이라
제어 도구가 닫지 않는다(H5). 생성 handle/worktree/agent 정체와 종료 책임을 02-kickoff에 기록한다.
**회수가 실제 프로세스를 닫았다고 가정하지 않는다.**

## 3. 구현 일감 발급

- 일감 명세에 담을 것: 고정한 기준 commit, 승인 범위·기준 유지, **네이티브 실행 관문(`.agents/rules/validation.md`)에서 최소 1회 실행한
  원자료 필수**, 범위·기준 변경이 필요하면 『질의응답』으로 멈추기, 제품 커밋·raw 기록 후 완료 보고,
  그리고 raw 를 쓸 작업 폴더 절대경로, **트래커를 쓰면 첫 단계로 일감 조회 결과(또는 실패 원문)를 원자료로 남기기** (능력 계약 H4).
  **이 일감이 돌릴 관문 층**도 적는다 — 구현·수정 라운드는 빠른 확인만, 수렴 뒤 일감은 최종 관문 전체(SKILL §5 「테스트 계층」).
- **시도·실패 기록**도 일감 명세에 넣는다: 워커는 구현·수정 중 시도 → 실패 → 원인 → 해결을 날짜와 함께
  `raw/<도구>/worklog.md` 에 덧붙인다(라운드를 넘겨 한 파일). 게이트 ② devlog 의 LLM 절 재료다(SKILL §8) —
  코디는 워커에게 따로 묻지 않고 이 파일을 읽는다.
- 『감독 워커 기동』으로 띄운다. **pane 재사용 경로와 새 기동 경로는 하나만 쓴다** — 재사용 pane은 기동
  때의 도구를 그대로 쓴다. **어떤 인자를 붙이고 빼는지는 매핑의 재사용 인자 규칙을 따른다** — 무시·거절되는
  인자도, 반대로 재사용 때만 **추가로 요구되는** 인자도 도구마다 다르다.
- **요약이 아니라 단계별 결과를 읽고 기록한다.** 실패한 단계는 앞 단계를 되돌리지 않고 남은 자원으로
  보고된다. 새 일감·시도 식별자와 주입 확인값을 저장한다.
- **복구는 2단이다**: 『화면 관측』으로 화면을 보고 차단 화면이면 치운 뒤(**trust는 사람 몫**) **같은 일감에**
  pane 재사용으로 다시 부른다. 주입이 확정되지 않은 시도는 같은 시도로 재개되고, 이미 주입된 시도가 열려
  있으면 거절된다. 재개로 수렴하지 않는 상태는 사람이 pane을 읽고 그 시도를 끝낸다.
  거절 코드의 정확한 뜻과 재개 조건은 매핑에서 읽는다.
- 보존(retain)은 **보존 의사 기록이며 새 일감 배정이 아니다.** 재사용 실패·세션 종료·사용자 takeover면
  상태를 확인하고 새 세션에 진행 증거를 인계한다 — 새로 기동했다면 동일 세션으로 재개했다고 쓰지 않는다.
- 구현 완료 후 수정 가능성을 위해 동일 워커를 유지하는 요청도 기록하고 보존한다.
  **코드 리뷰는 리뷰어마다 새 세션**에서 고정 구현 commit을 본다(구성은 SKILL §5·`.agents/defaults.md`). 리뷰 완료 후 수정 일감은 위와 같은 재사용 경로이고, **재리뷰는 새 리뷰 세션으로 기동한다.**
  코드 수정은 최대 3회에 누적한다. 미수렴 시 사용자 보고.
- 진행 중 구현 일감에서 승인 범위·기준을 바꿔야 하면 워커는 근거를 raw 에 남기고 『질의응답』으로 대기한다.
  아직 실행 중인 시도 위에 같은 pane의 새 시도를 겹쳐 기동하지 않는다.
- 경쟁 구현(`.agents/defaults.rules.md` 「경쟁 구현」)이면 후보마다 **모델·effort를 명령에 명시한다**(없으면 세션 기본을 탄다).
  느린 도구는 타임아웃이 잦으므로 대기 예산을 넉넉히 잡는다.

## 4. 완료·취소 후 정리 — 『회수·정리』

- 끝난 모든 시도의 회수 결과를 확인한다. 실패로 끝난 것도 정리 대상이다.
- **사람이 만든 pane은 빌린 것이라 보존된다**(H5). 원자료를 회수한 뒤 handle·worktree·도구 정체,
  활성 시도 없음, 사용자 takeover 없음, 이번 작업 전용임을 확인한 **경우에만** 직접 닫아 정리한다.
  불확실하면 보존하고 차단 사유를 보고한다. **회수 결과가 불확실한 상태를 두 번째 강제 종료로 우회하지
  않는다** — 매핑이 지정한 조회 명령이 복구다.
- 재사용된 옛 시도의 회수로 현재 워커가 정리됐다고 가정하지 않는다. 최종 시도와 실제 소유권을 확인한다.
- 사용자 확인용 worktree는 PR 생성 승인까지 유지한다 — 승인 뒤 코디네이터가 PR 을 연 뒤 같은 코디네이터가
  본체 경로에서 `scripts/task-finish.sh` 로 작업·구현 worktree 를 정리한다(작업 브랜치는 원격 PR head 로 남는다, SKILL §8).
  **pane 유지와 worktree 유지의 수명은 다르다.**
- **부하 장치·측정 프로세스는 띄운 쪽이 PID 를 기록하고 반드시 끈다** — 워커·리뷰어 모두. 인계 전 잔존 확인은
  이번 작업의 인스턴스만이 아니라 **부모가 init/launchd(PPID 1)로 바뀐 고아 프로세스**까지 본다(`ps -Ao pid,ppid,etime,command`) —
  남은 부하 장치가 뒤 작업의 측정을 오염시킨다.
- 역할별 사용량은 도구가 제공하는 값만 기록한다. 제공되지 않는 토큰·비용·절감률을 추정해 실측으로 보고하지 않는다.
