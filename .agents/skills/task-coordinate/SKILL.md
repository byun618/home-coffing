# task-coordinate — 코디네이터 절차 (작업 worktree 세션에서 실행)

전제: task-start 가 만든 작업 worktree(`.claude/worktrees/LIFE-NNN-<슬러그>/`, 작업 브랜치 체크아웃) 안이다.
브랜치 규약·게이트 위치는 AGENTS.md, 역할별 모델·effort는 `.agents/defaults.md`, 리뷰어 전환 예외는 `.agents/defaults.rules.md`,
완료 조건·네이티브 실행 관문은 `.agents/rules/validation.md`. **트래커를 쓰면 일감 상태 전이 시점은 이 문서 §1·§4·§5 첫 줄**(진행 중은 task-start).
문서 산출물·원자료는 전부 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/`(절대경로)에 둔다(AGENTS.md 「산출물 규칙」).
게이트 시점에 그 폴더만 커밋·push 한다. 작업 브랜치에는 코드만 들어간다.

**이 문서에는 도구 명령이 없다.** 능력 이름은 겹낫표로 감싸 적고, 그 능력을 어떤 명령으로 수행하는지와
무엇까지 증명되는지는 **`.agents/harness/capabilities.md`**(하네스 능력 계약)과 그 폴더의 도구별 매핑에 있다.
어느 매핑을 열지는 능력 계약의 「매핑 선택」 한 곳에서 정한다.

## 0. 실제 코디네이터 세션 확인

- `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/00-start.md`의 코디네이터·모델/effort·worktree를 확인한다.
  현재 세션과 기록이 다르면 작업을 시작하지 말고 `00-start.md`에 불일치를 기록하고 사용자에게 보고한다.
  재개 시 기존 Run·워커·승인 상태부터 확인하고 중복 기동하지 않는다.
- **이 세션에서** 트래커 일감 조회(트래커를 쓸 때), 웹 검색 도구의 사용 가능 여부, 지정한 외부 서치 도구의 사용 가능 여부(§1 2), 그리고
  선택한 매핑의 『전제 점검』을 실행한다. 시작 세션에서 됐다는 이유로 생략하지 않는다.
  MCP를 새로 등록했다면 실제 호출 도구로 나타나는지도 확인한다. 인증값은 문서·프롬프트에 적지 않는다.
- **『전제 점검』이 불일치를 내면 멈춘다.** 매핑이 요구하는 능력을 런타임이 광고하지 않으면 추측으로
  진행하지 않는다. 광고를 대조할 수 없는 도구(맨터미널)는 그 사실이 판정표의 공백이다.
- **이 작업이 쓸 에이전트 실행 파일(`.agents/defaults.md` 역할 표의 도구)을 셸이 찾을 수 있는지 따로 확인한다** —
  제어 런타임이 능력을 광고하는 것과 실행 파일이 설치돼 있는 것은 다르다. 없으면 그 역할을 다른 도구로
  몰래 대체하지 않고 차단 사유로 보고한다. 사전 승인된 예외 둘(지정 리뷰어 사용 불가 시 리뷰어 전환·외부 서치 한도 소진 시
  생략)은 `.agents/defaults.rules.md` 의 「리뷰어 사용 불가 시 자동 전환」·「외부 서치 한도 소진 시 생략」이 원본이다 — 조건·확인 방법·기록은 거기만 따른다.
- 빠진 도구·권한은 설정을 점검하고 남은 차단 사유를 시작 기록·사용자에게 보고한다. 임의로 다른
  코디네이터로 바꾸거나 필수 리뷰를 생략하지 않는다.
- 통과하면 `00-start.md`를 `준비 완료`로 갱신·커밋한다. 분석·기준·판정은 코디네이터, 구현은 별도 워커다.
- `.agents/rules/` 를 단계마다 읽는다: 글 전 writing.md, 코드 전 coding.md, 완료 판정 전 validation.md.
  디렉터리의 자동 로딩 여부에 기대지 않는다.

## 1. 분석 — 4박자 (외부 서치가 수 분 걸리므로 순차가 아니라 겹친다)

트래커를 쓰면 일감을 분석 중으로 전이한다(상태 이름·방법은 task-start 1·5단계의 D3 슬롯).

1. **일감 본문 확보**: 트래커에서 LIFE-NNN 상세를 읽는다(트래커가 없으면 사용자 지시 원문). 작업 폴더 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/` 는 task-start 가 만들어 둔다.
   **읽은 본문을 `00-analysis.md` 에 스냅샷한다** — 워커가 트래커를 못 읽어도 내용이 빠지지 않는다 (능력 계약 H4).
2. **외부 서치 — 코디 자체 서치가 먼저, 외부 서치 도구는 판단해서 띄운다**: 코디네이터의 웹 검색(런타임이 제공하는
   웹 검색·페이지 열기 도구) + 코드 읽기 + 짧은 실측을 수 분 하고 나서 외부 서치 도구
   기동을 정한다. 시작과 동시에 띄우지 않는다. 지정한 외부 서치 도구가 없으면(아래 슬롯이 「없음」) 코디 자체 서치로 닫고 생략 기록만 남긴다.
   <!-- paddock:design D13 -->
   grok — `grok-search` 스킬(Claude Code·Codex 공용). 한도·로그인은 `grok_status` 로 확인한다. 예: Expo SDK 54·expo-router 6·NativeWind,
   MikroORM 6, NestJS 11, EAS Build 의 동작·버전 이슈가 기준이나 범위를 바꿀 때.
   <!-- /paddock:design -->
   - **띄우는 조건** (하나라도 해당하면 기동): ① 판정 기준·범위가 외부 도구의 동작·버전·이슈 트래커에 걸려 있다
     (사용하는 CLI·라이브러리·외부 서비스의 동작, upstream 수정 여부 등) ② 자체 웹 검색이 빈약한데 그 사실이 기준·범위를 바꿀 수 있다
     ③ 일감 본문의 사실 주장을 레포 안에서 검증할 수 없다.
     셋 다 아니면 생략한다(원인이 레포 코드에 있고 실측으로 닫히는 경우). **애매하면 띄운다** — 병렬이라 진행을 막지 않는다.
   - **생략 기록**: `00-analysis.md` 서치 표에 「외부 서치 생략 — 사유(위 조건 중 무엇이 아니었는지)」를 적고 교차 대조 칸은
     **공백**으로 둔다. 게이트 ⓪ 보고에 한 줄 넣는다 — 사용자가 뒤집을 수 있다.
   - **띄우면** 별도 세션으로 병렬 위임한다 —
     『세션 기동』(외부 서치 도구) → 『준비 대기』 → 『본문 주입』(질문) → 결과를 파일로 저장시키고 『화면 관측』으로 회수.
     **외부 서치 도구용 전역 스킬이 있으면 리서치 규칙만 가져온다**(날짜 명시·파일 저장·호스트 검색과 대조) —
     그 스킬의 대화형 경로는 다른 제어 도구 기준이라 따르지 않는다. 결과는 자체 검색과 대조해 귀속한다.
     한도 소진이면 `.agents/defaults.rules.md` 「외부 서치 한도 소진 시 생략」대로 생략하고 멈추지 않는다.
3. **서치 대기 중 기준 초안** 작성 (§2)
4. **서치 취합 → 기준 확정**: 서치 결과가 기준을 바꿀 수 있다. 기준 freeze는 *킥오프 승인 시점*이다

- **선행 문서의 사실 주장을 대조표로 검증한다** — 일감 본문·00-project.md 의 전제가 틀렸을 수 있다.
  산출물: `00-analysis.md` (+ 외부 서치 원문 `00-analysis-search.md`)
- **learnings 를 골라 읽는다** — 코디가 이 분석에서 `.agents/learnings/` 를 README 「읽기」 대로 읽고, 맞는 항목을 `02-kickoff.md`
  제약에 인용한다.
- 절차가 이 스킬과 어긋나면 `00-analysis.md` 의 "절차 어긋남" 섹션에 누적 기록한다 (스킬 개정 재료)

## 2. 판정 기준 — `01-criteria.md`

- 항목별 통과선 + **필수 관문**: ① 실제 실행 + 재현 가능한 원자료 ② 추측 판정 금지 (실행 없는 칸 = 항목 무효)
  ③ **통과선을 낮춰 통과시킨 흔적이 없을 것**
  ④ **네이티브 실행 관문** — 정의는 `.agents/rules/validation.md`
- **선택한 매핑에서 공백인 능력은 통과선으로 쓰지 않는다.** 그 항목의 결과 칸은 공백이고 판정은 보류다.
- **경량 경로**(§3)면 기준은 핵심 항목 3~5개로 둔다. 필수 관문 ①~④는 그대로다 — 네이티브 실행 1회 원자료도 필요하다.
  명시 실행 목록(원장)은 만들지 않는다.
- **관문마다 「빠른 확인」 인지 「최종 관문」 인지 적는다** (§5 「테스트 계층」). 빠른 확인 = 수 분 안에 끝나는 것.
  최종 관문 = 나머지(무거운 시험·전후 비교·네이티브 실행·판정표 집계 등). 네이티브 실행은 최종 관문으로 미뤄도 생략하지 않는다.
  <!-- paddock:design D7 -->
  빠른 확인 = 타입체크(`apps/api`·`apps/app` 각각 `npx tsc --noEmit`) + `pnpm build`. 자동 테스트는 아직 없다(test 스크립트·*.spec.ts 없음).
  최종 관문 = 빠른 확인 + 일감 관문 스크립트 + 네이티브 실행(validation.md). base 에서 `pnpm lint` 는 실패(eslint 미설치)하고 app 타입체크는
  오류 1건(`app/records/[id].tsx`)이 있다 — 이 둘은 「base 대비 새 오류 0」으로 정의한다.
  <!-- /paddock:design -->
- **레포 전체 장치(lint·typecheck·검사 스크립트·시험 묶음)를 통과선으로 쓰면 기준을 동결하기 전에 base 에서 한 번 돌린다.** base 부터 실패하면 처음부터
  「base 대비 새 문제 0」처럼 차이로 정의하고, 외부 입력이 필요한 장치는 그 입력을 기준에 같이 적는다 — 결과를 본 뒤 통과선을 고치면 ③을 어긴다.
- 기준 없이 구현 시작 금지

## 3. 킥오프 문서 — `02-kickoff.md` (구현 워커와 리뷰어의 공통 기준)

- **설계는 워커가 흡수한다.** 코디네이터는 범위·제약·물류·검토 절차를 정하고, 구조·라이브러리·계측은
  워커 재량이다. 별도 설계 문서·설계 리뷰 단계는 없고 접근 타당성은 코드 리뷰에서 함께 본다.
- **경로 — 경량 / 전체**: 코디가 제안하고 근거를 한 줄 적는다. 사용자가 게이트 ⓪에서 확정하거나
  바꾼다. 시작 시 사용자 지정이 있으면(`00-start.md`) 그대로 따른다.
  - **왜 이 축인가**: 전체 경로가 더하는 것은 명시 실행 목록(원장)과 확장된 판정 기준이다. 원장은 판정이 실행의
    반복에 걸릴 때 「재실행하면 통과」·「예산을 늘려 통과」를 막고, 확장 기준은 런타임·영속·원격 상태의 놓친 경로를 막는다.
    그 위험이 없는 변경에는 원장이 지킬 것이 없다 — 그래서 경로는 변경 위치가 아니라 이 위험으로 가른다.
  - 경량: 바뀐 것이 전부 아래 경량 범주 안이고 세 조건을 모두 만족하는 변경. 판정 기준 축소, 실행 원장 생략(§2·§6).
    - 조건 ⓐ 아래 「전체로 올리는 것」을 하나도 건드리지 않는다
      ⓑ 되돌리기가 그 커밋 revert 로 끝난다 — 원격 상태·사용자 데이터·설치본을 따로 복원할 필요가 없다
      ⓒ 판정이 실행의 반복·통계(재실행 회차·대기 예산·성공률)에 기대지 않는다
    - 경량 범주 — **닫힌 목록이다.** 목록 밖의 변경(코드·워크플로·설정 등)은 전체다.
      <!-- paddock:design D8 -->
      - 문서·산문(README·docs·`spec/*.md` 서술) — 명령 블록을 바꾸지 않을 때만
      - 화면 카피·아이콘·NativeWind 클래스 — 로직·분기·데이터 흐름이 그대로일 때만
      - 목록 밖은 전체
      <!-- /paddock:design -->
  - 전체 — 「전체로 올리는 것」: 아래 하나라도 건드리면 전체다. **문서·스킬 일감이어도 그렇다** — 절차 문서의 바뀐 명령 블록·단계가
    원격 상태나 사용자 자원(로컬 브랜치·worktree·사용자 데이터)을 바꾸면 문서만 고쳤어도 전체다. 명령 블록·단계를 바꾸지 않은 설명 문구 개정은 경량이다.
    <!-- paddock:design D8 -->
    - entity·DB 스키마 변경(schema:update 영향), `packages/shared-types` DTO(API↔App 경계), 인증·가족 공유(admin/member) 권한 분기,
      `spec/event-taxonomy.md` 이벤트 정의, `Dockerfile`·`eas.json`·`app.config.ts`(versionCode·android.package)·배포 워크플로
    <!-- /paddock:design -->
    - 원격 상태 쓰기 — 저장소 설정·브랜치·태그·릴리즈, 외부 서비스에 쓰는 경로. 그 명령(태그 push·PR 생성·브랜치 삭제 등)을 담은 절차 문서의 바뀐 명령 블록·단계 포함
    - 배포·PR·정리 스크립트의 동작 — 패키징 설정(패키지 식별자·버전·권한·서명·빌드 프로필) 포함
    - 판정 장치 — 검사 스크립트와 그 스크립트가 입력으로 읽는 선언(하네스 매핑의 선언 블록)·문구 대조표, 테스트의 판정 로직과 기대값(정적 값을 따라 바뀐 것 말고),
      판정에 쓰이는(테스트·검사·관문의) 대기 예산·시간초과·임계값, 테스트 러너·린트·타입체크 설정. 숫자 하나여도 정적 값이 아니라 판정 장치다
    - 그 밖에 되돌리기 비싼 변경 — 이력 재작성·사용자 데이터 이전처럼 revert 로 돌아오지 않는 것
  - **애매하면 전체다.**
  - 게이트 ⓪①②, 네이티브 실행 관문, 새 세션 재리뷰, 수렴 조건·수정 상한은 경로와 무관하게 같다.
  - 구현 중 경량 일감이 전체 경로 대상을 건드리게 되면 범위 변경이다 — 전체로 바꿔 재승인을 받는다(§4.1).
- 정체 표: 브랜치 / worktree / **선택한 하네스 매핑** / **경로** / 격리 리소스 / 원자료 경로 / 결과 파일
- `00-start.md`의 코디네이터 선택과 지정 모델·effort를 정체 표에 옮긴다(재선택 금지). 구현 워커·
  코드 리뷰어의 모델/effort와 실제 명령을 구분하고 handle/브랜치 실제 반환값도 기록한다.
  매핑에 advisor 지정 능력이 없으면 그 칸은 공백으로 적는다.
- **경쟁 구현을 쓸 경우 발동 근거를 여기에 적는다** (`.agents/defaults.rules.md` 「경쟁 구현」의 조건 중 무엇인지).
  적지 않으면 단독이다.
- **격리 규칙**: 사용자가 실제 쓰는 리소스를 건드리지 않는다.
  외부 도구 실측은 전용 격리 인스턴스에서. 상대 브랜치 보지 않기, 작업 브랜치에 커밋하지 않기.
  제어 문맥은 『제어 문맥 격리』를 따른다 — 남의 Run·pane 을 밟지 않고, 바꾼 바인딩은 바꾼 쪽이 복원한다.
  <!-- paddock:design D6 -->
  - homelab 호스트 MySQL(스키마 `home_coffing`)은 공유 자원 — 새로 띄우지 않는다. `schema:update`·`schema:drop`·`db:reset` 은 사용자 승인 없이
    실행하지 않는다(파괴적, 운영과 같은 서버). 로컬 `.env` 가 운영 스키마를 가리키는지는 확인 필요 — 확인 전엔 운영으로 간주한다
  - 한 번에 하나만: DB 스키마 변경, 실기기 dev client(Metro 8081), 로컬 API 포트(3001)
  - 커밋하지 않는다: 루트 `.env`·`apps/app/.env`(시크릿), `backups/`(DB 덤프), DB 덤프·조회 결과 사본
  <!-- /paddock:design -->
- 원자료 규칙: 로그·스냅샷·타이밍 원본을 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/raw/<도구>/` 에 둔다 — 워커·리뷰어가 절대경로로 직접 쓰고
  코디가 게이트 시점에 커밋한다. 판정표 "근거" 칸이 가리킬 실물이 없으면 그 항목은 무효
- **트래커를 쓰면 일감 명세의 첫 단계는 "일감 조회 결과를 원자료로 남기거나, 못 읽으면 그 사실과 오류 원문을 원자료로
  남긴다"** 로 둔다 (능력 계약 H4) — 워커가 본문을 읽었는지를 파일로 판정할 수 있게 한다.
- **결과 문서**: 전부 작업 폴더에 + `raw/<도구>/DONE.md` (한 줄 요약 + 미완 목록) — 감사 추적용 기록이지
  완료 감지 신호가 아니다. 완료 감지는 §4 의 『완료 감지』로 한다. "작업 폴더에 없는 결과는 없는 것이다"

## ⛔ 승인 게이트 ⓪ — 킥오프 (§3 후 · §4 전, 『감독 워커 기동』 금지 지점)

00-analysis · 01-criteria · 02-kickoff 를 작업 폴더에 커밋한 뒤 사용자에게 보고하고 **멈춘다**:

- **문제 정의·범위**: 뭘 구현하기로 했고, 뭘 명시적으로 뺐는지 (분석에서 좁힌 결과)
- **판정 기준 요약**: 01-criteria 통과선 핵심 몇 줄
- **경로**: 경량 / 전체 와 근거 한 줄 — 사용자가 여기서 확정한다
- **진행 방식**: 단독 구현(또는 경쟁 발동 근거), 역할별 모델/effort·advisor

승인이 오면 §4 로 진행한다. 지적이 나오면 문서를 고쳐 재보고한다 — 기준 freeze 는 이 승인 시점이다.
이후 승인된 범위·기준이 바뀌면 구현을 멈추고 갱신 문서를 커밋해 재승인을 받는다.

## 4. 구현

트래커를 쓰면 일감을 개발 중으로 전이한다. 역할 구성은 `00-start.md` 를 따른다(설정 재질문 금지).
워커는 수정 라운드까지 유지하고, 리뷰어는 별도 세션이다.

**요청한 모델·advisor 가 실제로 무엇으로 해소됐는지는 『세션 기동』의 관측으로 확인한다** — 별칭은 버전
고정이 아니고, 기동 시점 스냅샷은 갱신되지 않는다. 요청값과 관측값을 구분해 기록한다. 모델
접근·사용량으로 기동할 수 없으면 차단을 보고한다 — advisor를 조용히 빼거나 다른 모델로 대체하지 않고, 기존 작업의 승인된 구성은 소급 변경하지 않는다.

**기동 전 [구현 워커 실행 절차](references/implementation.md)를 읽는다** — 산출물 소유권, 워커 보존·재사용·
종료, advisor 원칙이 거기 있다. 명령은 선택한 매핑에서 읽는다. 경쟁 구현이면 후보별 구현·리뷰·판정 파일과
리뷰 세션을 분리하고, 각 후보가 같은 기준을 받되 상대 구현·리뷰·판정을 워커에게 공유하지 않는다.

### 4.1 구현 지시와 진행

- 킥오프 승인 후 `implement` 일감을 발급하고 『감독 워커 기동』으로 워커를 띄운다. 워커는 구현 브랜치에서
  구현·검증하고 제품을 커밋하고, raw 는 작업 폴더 `raw/<도구>/` 에 직접 쓴 뒤 『완료 감지』가 받는 완료 보고로 끝낸다.
- 일감 명세에 기준 문서의 **산출물 커밋 해시와 작업 폴더 절대경로**, 원자료 규칙, **네이티브 실행 관문**을 명시한다.
  워커는 그 경로를 읽는다 — 킥오프 뒤 코디가 기준 문서를 고치면 『질의응답』이나 새 일감으로 알린다(조용히 바뀌지 않게).
  격리 인스턴스만으로 통과 보고하지 않도록 지시한다.
- 구현 중 승인된 범위·기준이 바뀌어야 하면 워커는 근거를 raw 에 남기고 『질의응답』으로 멈춘다.
  코디네이터는 범위·기준 변경이면 사용자 재승인으로 돌아가고, 그 외는 판단해 답을 보내 재개시킨다.
  세부 코드·구조 선택은 워커 재량이다.
- 구현 완료 후 수정 라운드를 위해 워커를 『회수·정리』의 보존 쪽으로 남긴다.

### 4.2 완료·질문·복구 공통 규칙

먼저 선택한 매핑을 읽어 Run/일감/시도 식별자와 플래그를 확인하고 기록한다 — **명령·플래그·수치 상한을
짐작해서 치지 않는다.** 완료는 파일 존재나 TUI idle이 아니라 해당 일감·그 시도의 완료 보고로 확인하며,
성공·실패 **모두 종료 보고다**(실패를 성공으로 처리하지 않는다).

- **한 배치의 모든 메시지를 처리한 뒤** 각 종료 워커의 재사용·보존·회수를 결정하고 나서 확인(ACK)으로
  이어간다. 확인 전에는 같은 배치가 계속 돌아온다. 같은 Run 의 대기를 중복 실행하지 않는다.
- **타임아웃·빈 배치는 새 워커를 만드는 근거가 아니다.** 응답 유실이 의심되면 요청·시도 조회로 기존
  요청과 실행을 먼저 확인한다 (『완료 감지』).
- 실행 중인 워커를 회수하지 않는다. **회수 결과가 불확실한 상태를 강제 종료로 우회하지 않는다** —
  매핑이 지정한 조회 명령이 복구다.
- **차단 화면(승인·업데이트·trust)은 워커의 질문이 아니다.** 질문은 워커가 『질의응답』으로 보낸 것만이다.
  차단은 『준비 대기』·『감독 워커 기동』의 거절로 나타나고, 가려내는 방법은 매핑마다 다르다.
  차단 화면을 가리지 못하는 도구에서는 첫 지시 전에 『화면 관측』을 반드시 한 번 한다.
- **배달·완료 증명이 공백인 도구에서는 『세션 기록 오라클』로 사후 확인만 할 수 있다** — 관측이므로
  완료 판정 칸의 근거로 승격하지 않는다. 기록이 없는 것도 실패의 증거가 아니다.

## 5. 독립 코드 리뷰

트래커를 쓰면 일감을 검증 중으로 전이한다. 수정 라운드·PR 대기 동안에도 검증 중을 유지한다(forward-only) — 세부 단계는 작업 폴더에 적는다.

- **리뷰어 구성은 `.agents/defaults.md` 의 역할 표가 정한다** — 라운드마다 기동 직전에 하는 지정 리뷰어 사용 가능 확인과
  자동 전환 조건은 `.agents/defaults.rules.md` 「리뷰어 사용 불가 시 자동 전환」이 원본이고, 구성을 바꾸면 「리뷰어 구성 변경 기록」에 남긴다.
  판정문에 실제 구성을 적는다. 구성이 여럿이어도 아래 규칙은 리뷰어마다 같다.
- `.agents/agents/reviewer.md`를 먼저 읽는다. 리뷰어는 서로, 그리고 구현자·코디네이터와 각각 별도 세션이며
  고정 구현 commit과 실제 실행 원자료를 검토한다. 설계 문서가 없으므로 접근 타당성도 여기서 본다.
  자기 구현분도 리뷰한다 — 구현자와 같은 도구라도 새 세션이면 검출력이 유지된다.
- 기동: 『감독 워커 기동』(감독 경로가 없는 도구면 『세션 기동』+『준비 대기』+『본문 주입』)으로 띄우고
  모델·effort를 `.agents/defaults.md` 대로 명시한다. **리뷰어마다 일감을 따로 발급한다** — 같은 일감으로 띄우면
  미확정 시도만 조용히 재개되거나 이미 열린 시도 때문에 거절된다. 리뷰어는 제품 파일을 수정하지 않는다.
- 큰 스펙은 매핑이 제공하는 **파일 전달 경로**로 넣는다 — 본문 길이 상한에 걸려 잘리면 리뷰 근거가 달라진다.
- 결과는 리뷰어 보고서 `raw/review/<도구>-rN.md`(예: `raw/review/reviewer-r1.md`) — 자기 관측/미실행과 다른 리뷰 근거를
  구분한다. 리뷰어가 작업 폴더에 직접 쓰고 코디네이터가 커밋한다. 리뷰 중 구현자는 제품 변경을 멈춘다.
- **코디네이터의 라운드 기록은 `reviews.md` 한 파일에 덧붙인다** — 라운드마다 `## rN` 절 하나에 리뷰 명세
  (고정 commit·리뷰어 지시)·지적 취합·판정·수정 명세를 차례로 쓴다. 라운드별 파일을 만들지 않는다. 다시 읽을 때는 최신 절만 읽는다.
- 외부 서치 도구가 리뷰에 들어가면 외부 사실 대조를 추가로 맡는다.
- **수정 라운드의 재리뷰는 반드시 새 리뷰 세션으로 기동한다.** 같은 세션 반복은 검출력이 오르지 않는다.
- 코드 수정 라운드는 같은 구현 워커에 새 일감·새 시도로 이어 맡기며 §4.2의 대기·확인을 따른다. 미해결 지적을 추적하고 세션 보존·정리는 실행 절차를 따른다.
- **테스트 계층 — 라운드는 구현 → 리뷰, 무거운 관문은 수렴 뒤 한 번**:
  - 구현·수정 라운드의 워커는 리뷰 전에 **빠른 확인**(§2)만 돌리고 원자료를 남긴다 — 깨진 코드를 리뷰로 보내지 않기 위한 것이다.
  - 리뷰가 수렴하면(높음·중간 0, 낮음 수정까지) 워커에 **최종 관문** 일감을 한 번 낸다. 코디는 결과를 독립 재실행해 verdict 근거로 쓴다.
  - 최종 관문이 실패하면 고친다. 수정이 기능·판정 경로를 바꾸면 **새 세션 리뷰를 1회만** 더 하고 최종 관문을 다시 돈다 —
    그 재리뷰에 높음·중간이 나오면 더 돌리지 않고 사용자에게 보고한다. 문서·대조 칸 추가만이면 재리뷰 없이 최종 관문만 다시.
  - 명시 실행 목록은 라운드·최종을 넘겨 누적한다(validation.md). 빠른 확인 회차도 행이다.
  <!-- paddock:design D7 -->
  빠른 확인 = `(cd apps/api && npx tsc --noEmit) && (cd apps/app && npx tsc --noEmit) && pnpm build` (app 은 base 오류 1건 대비 새 오류 0),
  최종 관문 = 빠른 확인 + 작업 폴더 `scripts/` 관문 + 네이티브 실행 1회.
  <!-- /paddock:design -->

## 6. 취합·판정 — `verdict.md`

- **리뷰·구현 raw/ 가 작업 폴더에 다 있는지 확인하고 커밋한다** — 회수할 브랜치는 없다. 경쟁이면 탈락
  후보 raw도 보존한다. 구현자의 파일을 코디네이터가 직접 고치지 않는다.
- 구현 HEAD를 `LIFE-NNN-<슬러그>-<도구>-final`로 고정한다. 단독 구현에 비교 승자/탈락 후보를 꾸며 쓰지 않는다.
- **`verdict.md` 는 라운드 요약표(라운드·대상·높음/중간/낮음·채택/기각)와 판정표만 둔다.** 지적별 판정·사유는
  `reviews.md` 에 있고 verdict 에 다시 옮겨 적지 않는다 — 링크만 건다.
- 판정표는 `.agents/rules/validation.md` 의 7칸 형식이다 — **원장 칸과 실행 n/총 m 칸을 비워 두지 않는다.**
  경량 경로면 두 칸에 `해당 없음 — 경량 경로` 를 적는다(validation.md).
  선택한 매핑에서 공백인 능력에 기대는 항목은 결과 칸을 공백, 판정을 보류로 적는다.
- **단일 리뷰어 지적을 다수결로 기각하지 않는다. 전원 침묵을 통과 근거로 쓰지 않는다** —
  리뷰어가 모두 놓친 높음 결함은 게이트 ① 사용자 확인이 잡을 수 있다. 단독 리뷰면 사용자 확인의 비중이 더 크다.
- **리뷰어의 "구조를 버리고 다시 쓰라" 류 지적은 코디네이터가 독립 재현한 뒤 채택한다.**
- **advisor 조언은 지적이 아니다** — diff 에서 재현 가능한 것만 지적으로 세고,
  advisor 동의를 교차 확인 근거로 쓰지 않는다.
- 기각·탈락엔 사유 기록, 자기 구현분 지적 기각은 특히 상세히.
  경쟁이면 자기 구현 브랜치에 대한 자기 리뷰는 승자 판정 근거로 세지 않는다.
- 수렴: 높음+중간 0건 → 낮음 모아 1회 수정 → 최종 관문(§5 테스트 계층) 후 종료. 수정 상한 3회(미수렴 라운드의 수정만 센다 — 수렴 뒤 낮음 1회 수정은 상한 밖), 미수렴이면 사용자 보고

## 7. ⛔ 승인 게이트 ① — 채택

판정 결과를 사용자에게 보고하고 **멈춘다**. 이 시점엔 머지 0건 — 채택안 변경·추가 수정 요구가 가능하다. 조용한 완료 금지.

## 8. (채택 승인 후) 작업 브랜치 머지 → 사용자 확인 → ⛔ 승인 게이트 ② — PR 생성 승인

```bash
git merge <기록된_구현_브랜치>                      # 채택 구현 → 작업 브랜치
```

- 머지 후 사용자에게 알린다: **작업 worktree 에서 통합 결과를 직접 실행·확인해 달라**
  (실행 방법을 한 줄로 같이 준다). 문제가 나오면 수정 라운드 → 재확인
  <!-- paddock:design D15 -->
  작업 worktree 에서 `pnpm install && pnpm dev` 후 안드로이드 실기기 dev client 로 해당 화면 확인(API 는 로컬 3001).
  <!-- /paddock:design -->
- **게이트 ① 사용자 수정 라운드**: 확인 중 나온 지시·결함은 범위를 `reviews.md` 의 `## 게이트 ① 수정 N` 절로 박고
  워커가 구현 브랜치에 이어 커밋(rN 태그) → 코디네이터가 diff 정독·게이트 재실행·스모크 원자료 검증 후 같은 절에 판정을
  덧붙이고 verdict 요약을 갱신 → 작업 브랜치 머지. 범위가 UI/문구 수준이면 전체 코드 리뷰를 반복하지 않는다
  (가드·기준 경로를 건드리면 재리뷰 판단). 워커 기동·대기는 §4 그대로다.
- **게이트 ② 기록 — 확인이 끝나면 PR 생성 승인을 요청하기 전에 쓴다.** 셋 다 작업 폴더 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/` 에 둔다.
  PR 에 싣지 않는다.
  채택 시점·방법은 `.agents/learnings/README.md`·`docs/adr/README.md` 를 따른다.
  - **devlog** `devlog.md` — 한 파일, 날짜별 절(`## YYYY-MM-DD`). 날짜마다 두 절:
    **사람**(그날의 결정·승인·지시 원문 — LLM 초안이고 사용자가 고친다. 감정·의도를 추측해 쓰지 않는다) ·
    **LLM**(시도 → 실패 → 원인 → 해결).
  - devlog 재료: 코디 기억이 1차지만 compact 로 초반이 뭉개진다 — 날짜·사실은 코디 세션 transcript 와 git log(작업 브랜치·작업 폴더)로 대조한다.
    `reviews.md` 는 내용 대조에 쓴다 — 시각이 드물어 날짜 축이 되지 못한다.
    - **코디 세션 기록 찾기**: `00-start.md` 에 시작 세션이 적은 세션 기록 경로(task-start 4단계 — 『세션 기동』 응답이 돌려준 값)를 쓴다.
      코디가 재기동돼 경로가 여럿이면 날짜순으로 모두 읽는다.
      경로가 없으면(기동 응답에 경로를 주지 않는 도구, 또는 그 기록을 남기기 전에 시작한 일감) 경로를 짐작하지 않고(능력 계약 H6)
      devlog 에 「코디 기록 없음」을 적은 뒤 코디 기억·git log 로만 쓴다.
    - **읽기**: 매핑의 『세션 기록 오라클』로 사용자 입력·시각 등 필요한 줄만 뽑는다 — 기록을 통째로 문맥에 싣지 않는다.
      오라클은 관측이라 devlog 사실의 증명이 아니다.
    - 사람 절의 지시 원문은 사용자가 워커 pane 에 직접 친 입력을 놓칠 수 있다(H2 — 『화면 관측』으로만 회수된다). 사람 절 초안에 그 한계를 적는다.
    - 워커의 시도·실패는 워커가 구현 중 남긴 `raw/<도구>/worklog.md` 에서 읽는다(일감 명세 — [references/implementation.md](references/implementation.md) §3).
      모자라면 보존 워커에게 새 일감으로 받는다(『감독 워커 기동』 재사용 경로). 『질의응답』은 워커가 묻는 통로라 코디가 워커에게 묻는 데 쓰지 않는다.
  - **learnings 제안** `learnings-proposal.md` — 목적지 분류(`.agents/learnings/README.md`)를 거쳐 learnings 로 남을 배움만, 그 형식대로.
    rules·스킬 승격 제안이면 안 통하는 자리 세기·시나리오 열거를 붙인다. 작업 중 낡은 영역 파일(90일·상한 — README 「상한과 압축」)을 봤으면
    고치지 않고 그 파일 이름을 여기 적는다. 없으면 「없음」 한 줄.
  - **ADR 초안** `adr-draft-<제목-케밥>.md` — 오래 남을 결정이 있을 때만. `docs/adr/template.md` 로, 번호 없이 `status: proposed`.
  - **사람 절 확인은 정리 전에 끝낸다**: PR 생성 승인 요청 보고에 devlog 사람 절 초안과 learnings 제안·ADR 초안 요약을 싣는다.
    사용자 수정을 반영한 뒤 아래 1단계 커밋에 함께 넣는다 — 정리(3단계)가 코디의 마지막 실행이라 그 뒤엔 고칠 세션이 없다.
    사용자가 통합 확인과 PR 생성 승인을 한 응답에 주어도 같다 — 사람 절 초안을 보이고 사용자 확인을 받기 전에는 1단계로 가지 않는다.
- 확인이 끝나 사용자가 **PR 생성 승인**을 주면 — **승인하는 것은 PR 생성이다. main 머지가 아니다**:
  1. **게이트 ② 기록·인계 문서·PR 원고를 작업 폴더에 커밋한다** — `task-pr.sh` 가 거기서 읽는다.
     그 폴더를 push 한다. PR 에는 코드만 실린다.
     - `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/handoff-main.md`: LIFE-NNN, 본체 경로, 작업 브랜치·PR base(`main`),
       검증한 구현 커밋, 채택·PR 생성 승인 근거,
       트래커 일감의 현재 상태와 다음 전이(트래커를 쓸 때). **일감은 완료로 바꾸지 않는다.**
     - **PR 원고 `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/pr.md`**:
       기존 문서를 옮겨 붙이지 말고 diff(`git diff origin/main...HEAD`)와
       산출물을 읽고 **PR 을 읽는 사람 기준으로** 새로 쓴다. 첫 줄 `# <제목>` = PR 제목(무엇이 바뀌는지 한 줄, 일감 ID 접두(`<ID>:`)는 없으면 스크립트가 붙인다 — ID 없는 프로젝트는 붙지 않는다),
       나머지 = 본문: 왜(문제·증상) → 무엇을 바꿨나(사용자에게 보이는 변화 먼저, 구현 요점은 그 뒤) → 확인한 것(실제 실행 근거 한두 줄).
       리뷰 라운드·게이트·판정표 같은 내부 절차는 쓰지 않는다 — 판정문 위치는 스크립트가 붙인다.
       코드 레포가 공개될 수 있으므로 원자료 경로·내부 세션 정보를 본문에 옮기지 않는다.
       원고가 없거나 첫 줄이 제목이 아니면 `task-pr.sh` 가 push 전에 멈춘다.
  2. **작업 worktree 에서 PR 을 연다.** `task-pr.sh` 는 레포를 git 공통 디렉터리에서 찾으므로 작업 worktree 의 사본으로 돌려도 본체 레포를 가리킨다.
     - `scripts/task-pr.sh LIFE-NNN-<슬러그>` — 미커밋 거절 → push → main 대상 PR 생성(있으면 재사용, 멱등).
       본문은 `pr.md` 그대로에 판정문 위치·서명이 붙는다. `gh pr list --head LIFE-NNN-<슬러그>` 로 1건을 확인한다.
  3. **정리까지 한다.** 정리는 작업 worktree 를 지우므로 **코디 세션의 마지막 실행**이다 — 이후 도구 호출을 하지 않는다.
     `task-finish.sh` 는 작업 worktree 안 실행을 거절하므로 본체 경로에서 본체의 스크립트로 돌린다.
     - `cd <본체 절대경로> && scripts/task-finish.sh LIFE-NNN-<슬러그>` — PR 이 있고 로컬 작업 브랜치가 원격 사본과
       같음을 확인한 뒤 작업·구현 worktree, 로컬 브랜치, 구현 브랜치 원격 사본을 정리한다.
       작업 브랜치는 원격(PR head)에 남는다. 태그 `LIFE-NNN-<슬러그>-*-final` 은 유지한다.
  4. 사용자에게 스크립트 출력 원문과 함께 **PR 번호**, 인계 문서 경로
     `<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/handoff-main.md`(절대경로) 를 보고하고 "PR 생성·정리 완료"라고 끝낸다.
     트래커의 일감 상태는 검증 중 그대로다.
- 스크립트가 실패하면 멈추고 원문을 보고한다. 이미 연 PR 은 `task-pr.sh` 재실행이 재사용하고, 남은 정리는 같은 명령으로 이어 간다(멱등).
- 코디네이터가 직접 실행하는 것은 PR 생성과 정리까지다.
- 워커 pane 과 worktree 의 수명은 다르다 — worktree 는 PR 생성·정리까지 유지하고, pane 정리는 『회수·정리』를 따른다.
  빌린 pane 은 남으므로 따로 닫는다.
