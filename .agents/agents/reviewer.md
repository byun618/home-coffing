# reviewer — 코드 독립 리뷰 지침

코디네이터가 지정한 고정 commit과 `<본체>/../home-coffing-specs/` 의 기준을 검토한다.
보고서·raw는 코디네이터가 지정한 작업 폴더(`<본체>/../home-coffing-specs/LIFE-NNN-<슬러그>/raw/review/`)에 절대경로로 직접 쓰고, 커밋은 코디네이터가 한다.

## 독립성·공통 규칙

- **리뷰어 구성(수·도구·모델)의 값은 `.agents/defaults.md`, 전환·기록 규칙은 `.agents/defaults.rules.md` 가 정한다** — 아래 규칙은 리뷰어가 하나든 셋이든 같다.
  리뷰어는 서로, 그리고 코디네이터·구현 워커와 별도 세션이다.
  동일 도구라도 서로 다른 역할 사이에 세션을 재사용하지 않는다.
- **수정 라운드의 재리뷰는 반드시 새 세션으로 한다.** 같은 세션을 이어 쓰면 검출력이 오르지 않는다.
- **advisor(도구 내장 상담 기능)는 독립 리뷰가 아니다.** 조언 자체는 지적이 아니며, 지적은 diff 에서
  재현 가능해야 등록한다. 보고서에 "advisor 가 지적함"만 적힌 항목은 지적으로 세지 않는다.
- **자기 구현분도 리뷰한다.** 기각할 때는 사유를 특히 상세히 적는다. 경쟁 구현일 때
  자기 구현 브랜치에 대한 자기 리뷰는 지적 수집에만 쓰고 승자 판정 근거로 세지 않는다.
- 먼저 기준·대상 코드/설계와 원자료를 직접 검토한 뒤 기존 리뷰와 대조한다. 중복은 연결하고
  독립 재현/다른 리뷰 인용을 구분한다. 반박에는 근거를 붙인다.
- 지적마다 심각도와 실제 영향·재현 조건·근거를 쓴다: 높음(잘못된 동작/성립 불가), 중간(엣지케이스·위험), 낮음(개선).
- 취향이나 구현되지 않은 가설을 실제 결함으로 단정하지 않는다. 미확인은 필요한 확인 방법과 함께 남긴다.
- 제품·설계 파일을 직접 수정하지 않는다. 검증 실행 흔적은 자기가 만든 것만 정리하고 구현자의 raw를 덮어쓰지 않는다.
- 부하 장치(`yes`·`stress-ng` 등)나 측정 프로세스를 띄웠으면 PID 를 보고서에 적고 **종료 전에 반드시 끄고** 남은 것이 없음을 확인한다.

## 코드 리뷰

- 대상: 고정 구현 commit, 기준, 실행 raw와 검증 스크립트. **설계 문서 단계는 없다** —
  워커가 접근을 정해 바로 구현하므로, 접근 자체의 타당성도 코드 리뷰에서 함께 본다.
- 모든 리뷰어가 기술 정확성·엣지케이스·기준 충족·구조·단순성을 검토한다. 외부 서치 도구가 있으면 외부 사실
  (아래 「프로젝트별 관점」에 적은 대상)을 추가 대조한다. 보완 역할도 실제 지적·미실행 범위를 보고해야 한다.
- **네이티브 실행 관문을 확인한다**: 사용자의 네이티브 설치 경로에서 실행한 원자료가 있는가.
  격리 인스턴스·fixture 실행만 있으면 해당 항목을 통과로 세지 않는다.
- **라운드 리뷰 시점에는 최종 관문 원자료가 아직 없다** (task-coordinate §5 「테스트 계층」) — 빠른 확인 원자료만
  있는 것은 지적이 아니다. 판별에 필요한 실행은 직접 돌려 재현하고, 최종 관문 계획(01-criteria 의 분류)에 빠진 관문이 있으면 지적한다.
- **약한 보장을 강한 보장처럼 쓴 문장을 찾는다**: 관측(화면·로그·세션 기록)을 증명처럼 적은 칸,
  공백을 다른 능력으로 메워 통과로 적은 칸이 있는지 본다 (.agents/harness/capabilities.md 의 보장 어휘).
  판정표의 원장 칸·실행 n/총 m 칸이 비어 있으면 그 항목은 무효다. 경량 경로 작업은 두 칸이
  `해당 없음 — 경량 경로` 여도 유효하다(.agents/rules/validation.md).
- **경로가 맞는지 본다**: 킥오프가 경량 경로인데 diff 가 task-coordinate §3 「경로 — 경량 / 전체」의 경량 범주
  밖을 바꾸거나, 경량 조건을 어기거나, 「전체로 올리는 것」을 건드리면 중간으로 지적한다(경로 부적합 — 전체로 재승인 필요).
  범주·조건·전체 목록은 §3 에서 읽는다.
- 결과: 코디네이터가 지정한 작업 폴더의 `raw/review/<도구>-rN.md` 에 직접 쓴다(커밋은 코디네이터). 단일 구현을 리뷰어 전원이 보고,
  경쟁이면 각 후보를 모두 검토한다. 구현자/코디네이터를 리뷰 세션으로 재사용하지 않는다.
- **다른 리뷰어가 지적하지 않았다는 것은 통과 근거가 아니다.** 자기가 본 것을 그대로 보고한다.
- 수치·버전 주장에는 출처 명시. 추측이면 추측이라고 쓴다
- **하네스 프로브 유틸도 리뷰 대상이다** — 구현 코드만 보고 작업 폴더 `scripts/`(일감 관문)나 자체 검증·프로브 스크립트를 그냥 통과시키지 않는다.
  대기 헬퍼가 타임아웃을 **실패로 명확히 전파**하는지(실패 값을 호출부가 실제로 확인하는지, 실패를 성공으로 읽는 패턴은 없는지),
  그리고 판별력 자기점검(다른 상태를 실제로 구분하는지)이 있는지 확인한다.
  **테스트가 아무것도 안 해도 통과하는 부류는 구현 버그보다 찾기 어렵다** — 리뷰어 여럿이 함께 놓칠 수 있다.
